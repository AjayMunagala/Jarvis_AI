# JARVIS Core Architecture

## Current shape

This is a modular monolith. A single FastAPI process owns HTTP routing, configuration, provider selection, and the chat flow. `/chat` delegates to a Mother Orchestration service that classifies intent, plans bounded expert steps, executes configured experts and synthesizes validated outputs. Modules communicate through typed schemas and the `IntelligenceProvider` protocol.

- `jarvis/main.py`: application factory, validated startup settings, dependency construction, lifespan, and sanitized exception handling.
- `jarvis/core/config.py`: Pydantic settings, environment loading, and validation.
- `jarvis/core/logging_config.py`: structured JSON logs on the application logger. It preserves root/host handlers and excludes chat contents and exception messages/tracebacks; exception type is retained for diagnosis without logging potentially sensitive details.
- `jarvis/core/middleware.py`: caps HTTP request body bytes while receiving the request and returns a sanitized 413 response when exceeded.
- `jarvis/api/routes/`: health/readiness and chat HTTP endpoints.
- `jarvis/models/schemas.py`: public request and response contracts.
- `jarvis/intelligence/base.py`: vendor-independent provider protocol and sanitized provider failure types. `mock_provider.py` is the offline demonstration; `openai_provider.py` makes a bounded async Chat Completions request; `router.py` selects the adapter from validated settings. `schemas.py` validates normalized and provider response content.
- `jarvis/orchestration/`: request context, intent and plan contracts, deterministic classifier, bounded planner, configured expert/tool registries, executor, synthesis, and in-memory audit-event schemas.
- `jarvis/orchestration/config/experts.json`: enabled expert personas and intent routing. `tools.json` defines the tool registry contract and currently contains no tools.
- `tests/`: API behavior and configuration tests.

## Request flow

`POST /chat` is subject to the global request body byte ceiling, validates the message and optional UUID `conversation_id`, enforces the configured character ceiling, and passes an explicit request context to the orchestrator. If persistence is enabled, a missing ID creates a conversation and stores both messages atomically; a supplied ID appends to that existing conversation in the same transaction. Unknown IDs return 404 without creating replacements. If persistence is disabled, ordinary requests return a null conversation ID and a supplied ID returns 503. Deterministic keyword classification falls back to `general_inquiry` at confidence 0 if classification raises or returns an invalid result. The planner selects only enabled experts from the validated JSON registry and caps plans at five rounds. Sequential execution is the default; parallel execution requires the matching intent to be listed in `parallel_intents`, uses a semaphore, and is capped by validated settings. Provider output is validated with Pydantic before synthesis. Only explicit transient expert/provider failures are retried with bounded exponential backoff; attempts share the request deadline. Failed steps produce partial output when successful expert results remain. API errors use a common `error` and `detail` JSON envelope; `/chat` keeps its existing fields, adds `partial`, and adds nullable `conversation_id`. Chat successes, provider failures, and provider timeouts carry an `X-JARVIS-Execution-ID` correlation header. Oversized streamed request bodies are stopped and returned as 413; HTTP/1.x rejection responses request connection close so unread bytes cannot be reused as another request. Logs and in-memory audit events carry execution/expert metadata but exclude messages, output content, secrets, and exception details.

`GET /conversations/{conversation_id}/messages` is available only when persistence is configured. It validates UUID identifiers, returns a bounded page of at most 100 messages in ascending sequence order, and supports `before_sequence` to request older pages. Unknown IDs return 404; repository failures and disabled persistence return sanitized 503. The endpoint does not establish ownership or authorization: conversation IDs are not access-control tokens, and authentication/user isolation are not implemented.

Expert definitions are persona metadata, not seven independent agent implementations: each configured expert calls the same selected provider contract. `AnalysisExpert` and `ValidationExpert` have distinct configured system instructions and Pydantic output contracts. The analysis contract captures a summary, bounded factors, evidence-supported conclusions, assumptions, missing information, and recommendations. The validation contract captures findings with supported/contradicted/uncertain verdicts, rationale and evidence, plus assumptions, missing information, and recommendations. Supported or contradicted claims require evidence. The provider protocol accepts an optional response model; the OpenAI adapter sends it as Chat Completions strict `json_schema` output. It transforms a copied schema by removing string/array size-bound keywords and documented unsupported composition keywords, while preserving required fields, object closure, references, definitions, and type/enum structure. The [OpenAI Structured Outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs) documents `maxItems` for standard models but excludes array bounds for fine-tuned models; since the selected model is configurable and live compatibility is unverified, all array bounds are omitted from the request schema. Pydantic continues to enforce all original bounds and semantic validators on returned JSON before synthesis. Unknown schema keywords, invalid references, or non-closed/non-required objects fail with sanitized permanent errors before network I/O. Structured requests use a bounded 8,192 completion-token allowance (ordinary text remains at 1,024); a truncated structured completion is rejected. The mock ignores instructions and returns its existing deterministic text with `assessment_status=not_evaluated` and empty specialist collections. Synthesis renders validated fields as readable text; public `/chat` fields remain unchanged. Structured validation enforces shape and bounds, not semantic quality. Provider identity and the `demo` flag distinguish mock output from model output. The OpenAI adapter uses a configured key, model, endpoint and explicit connection/read timeouts; only 429, 5xx and transport timeouts are eligible for the orchestrator's bounded retries. Authentication, refusal, malformed output, truncation, and other permanent errors are not retried, and API errors/logs do not include provider response bodies or credential values. Mocked tests verify outgoing schema construction, not live endpoint compatibility. Tool definitions are configuration data only. There is no tool executor, permission gateway, persistence, or external action path in this milestone. Audit events are returned in the internal orchestration result and are not persisted or exposed in the public chat body.

## Adding capabilities and providers

Future model-driven planners/classifiers, memory, capability registry, tool runtime, permission gateway, retrieval, and independent verification modules should expose small typed interfaces and be assembled in the application/orchestration layer. Capability code should depend on those interfaces rather than a vendor SDK. A new model adapter implements `IntelligenceProvider`; configuration and router registration then select it. Keep credentials in environment-backed secret settings, never in logs or source. Tools that can affect external systems should be mediated by a separate permission/approval boundary and explicit bounded execution policy. The current OpenAI-compatible adapter makes only a text-completion request and does not expose tool calling.

## Reliability and future persistence

Current request processing has a configurable timeout and sanitized failure boundary. Optional conversation persistence is behind the `ConversationRepository` protocol; the PostgreSQL adapter is constructed only when `JARVIS_PERSISTENCE_ENABLED=true` and the psycopg persistence extra is installed. Connections use a bounded configurable connect timeout. A successful chat result is saved after orchestration as one transaction containing either a new conversation plus its first exchange or two appended messages on an existing conversation. Failure returns a sanitized 503 and does not report a saved success; an unknown supplied conversation ID is a distinct 404. The schema enforces UUID keys, allowed roles, nonblank bounded content, a conversation foreign key, and a unique per-conversation sequence index for deterministic reads. `GET /conversations/{conversation_id}/messages` returns bounded chronological pages with a sequence cursor. There is no audit/provider prompt persistence or automatic schema migration at app startup; use the existing database migration runner to apply `0002_conversation_persistence.sql`. Disabled mode does not import/connect to PostgreSQL. The health endpoint is process-level; readiness currently means startup configuration/provider/repository construction succeeded and does not probe the database.

The opt-in live PostgreSQL integration tests are isolated under `integration_tests/` so the ordinary offline unit suite does not require a server or PostgreSQL driver. They require an explicit environment opt-in, a password-free local-loopback maintenance URL, `PGPASSFILE`, the optional `persistence` dependency, and PostgreSQL client tools. The fixture creates a uniquely generated disposable database and removes only that database after the tests. Missing prerequisites are reported as skips; a skip is not evidence of live database compatibility. See [database/README.md](../database/README.md#opt-in-postgresql-integration-tests) for the exact PowerShell setup and safety constraints.
