# JARVIS Core Architecture

## Current shape

This is a modular monolith. A single FastAPI process owns HTTP routing, configuration, provider selection, and the chat flow. `/chat` delegates to a Mother Orchestration service that classifies intent, plans bounded expert steps, executes configured experts and synthesizes validated outputs. Modules communicate through typed schemas and the `IntelligenceProvider` protocol.

- `jarvis/main.py`: application factory, validated startup settings, dependency construction, lifespan, and sanitized exception handling.
- `jarvis/core/config.py`: Pydantic settings, environment loading, and validation.
- `jarvis/core/logging_config.py`: structured JSON logs on the application logger. It preserves root/host handlers and excludes chat contents and exception messages/tracebacks; exception type is retained for diagnosis without logging potentially sensitive details.
- `jarvis/core/middleware.py`: caps HTTP request body bytes while receiving the request and returns a sanitized 413 response when exceeded.
- `jarvis/api/routes/`: health/readiness, chat, conversation history, and memory-management endpoints.
- `jarvis/api/dependencies.py`: shared bearer-token verification and configured single-owner resolution for persistence-backed routes.
- `jarvis/models/schemas.py`: public request and response contracts.
- `jarvis/intelligence/base.py`: vendor-independent provider protocol and sanitized provider failure types. `mock_provider.py` is the offline demonstration; `openai_provider.py` makes a bounded async Chat Completions request; `router.py` selects the adapter from validated settings. `schemas.py` validates normalized and provider response content.
- `jarvis/orchestration/`: request context, intent and plan contracts, deterministic classifier, bounded planner, configured expert/tool registries, executor, synthesis, and in-memory audit-event schemas.
- `jarvis/orchestration/config/experts.json`: version-2 expert personas, ordered intent phrase rules, intent routing, and allowlisted structured-output contract IDs. `tools.json` defines the tool registry contract and currently contains no tools.
- `jarvis/memory/`: validated memory record/page contracts, repository protocol, and best-effort retrieval fallback.
- `jarvis/persistence/memory_postgres.py`: optional PostgreSQL memory adapter using the same connection timeout and secret URL conventions as conversation persistence.
- `tests/`: API behavior and configuration tests.

## Request flow

`POST /chat` is subject to the global request body byte ceiling, validates the message and optional UUID `conversation_id`, enforces the configured character ceiling, and passes an explicit request context to the orchestrator. If persistence is enabled, a missing ID creates a conversation and stores both messages atomically; a supplied ID appends to that existing conversation in the same transaction. Unknown IDs return 404 without creating replacements. If persistence is disabled, ordinary requests return a null conversation ID and a supplied ID returns 503. Ordered phrase rules from the validated version-2 expert registry drive deterministic keyword classification; unknown text falls back to `general_inquiry`, and classifier failures or invalid results fall back at confidence 0. The planner selects only enabled experts from the validated JSON registry and caps plans at five rounds. Sequential execution is the default; parallel execution requires the matching intent to be listed in `parallel_intents`, uses a semaphore, and is capped by validated settings. Provider output is validated with Pydantic before synthesis. After expert execution, deterministic provenance checks can locate structured evidence strings in eligible source text; this is separate from schema validation and does not assess logical consistency or factual truth. Only explicit transient expert/provider failures are retried with bounded exponential backoff; attempts share the expert-execution deadline. Failed steps produce partial output when successful expert results remain. API errors use a common `error` and `detail` JSON envelope; `/chat` keeps its existing fields, adds `partial`, and adds nullable `conversation_id`. Chat successes, provider failures, and provider timeouts carry an `X-JARVIS-Execution-ID` correlation header. Oversized streamed request bodies are stopped and returned as 413; HTTP/1.x rejection responses request connection close so unread bytes cannot be reused as another request. Logs and in-memory audit events carry execution/expert metadata but exclude messages, output content, secrets, and exception details.

### Evidence provenance

Pydantic schema validation checks output structure and field constraints. The separate provenance checker evaluates each structured evidence string after successful expert execution. It normalizes with Unicode NFKC, case-folding, and whitespace collapsing; punctuation is retained. A match is an exact normalized substring of either the original user request or another successful expert's `output.content` summary. The target expert's own output, other experts' evidence fields, retrieved memories, failed outputs, and provider prompts are not eligible sources. Outcomes are `source_match`, `unverified`, or `not_evaluated`. Work is bounded by source/evidence length and result/target counts; the 10,000,000-character work budget includes normalization input/output and comparisons. The request is always checked first. If request normalization or comparison cannot fit the remaining budget, the evidence is `unverified` and peer summaries are not checked, preventing fallback attribution to a source when the higher-priority request was unchecked. Peer summaries are considered in plan result order; duplicate expert identifiers are excluded as ambiguous. Mock mode skips evaluation deterministically. Missing or `None` evidence collections contribute no items; explicit malformed elements in a collection produce an `unverified` outcome when representable. The internal orchestration response carries outcome/source identifiers and indexes only; structured logs contain only bounded outcome counts. These checks establish text traceability only: they do not establish that the source supports a claim, detect logical contradictions, or determine factual truth. A user's statement or another model's output is not authoritative evidence.

`GET /conversations/{conversation_id}/messages` is available only when persistence is configured and authenticated. It validates UUID identifiers, returns a bounded page of at most 100 messages in ascending sequence order, and supports `before_sequence` to request older pages. Unknown IDs return 404; repository failures and disabled persistence return sanitized 503. Conversation IDs are not access-control tokens; the single configured bearer credential gates all persistent conversation operations.

`/memories` exposes authenticated explicit create, list, get, patch, delete, and lexical search operations against `jarvis_app.memories`. Migration `0003_long_term_memories.sql` adds bounded content, optional category/source reference, timestamps, and a GIN full-text index; migration 0004 adds nullable owner ID without default/backfill. The list route supports an optional exact `category` filter applied to both count and item queries, with pagination calculated against the filtered result set. Search uses `POST /memories/search` so search text is not placed in the request URL/access log; PostgreSQL `simple` text search and `ts_rank_cd` provide lexical ranking, with stable timestamp/UUID ordering for ties. This is not semantic search. Invalid UUIDs and bodies are rejected, foreign and missing records both return 404, and disabled/unavailable persistence returns sanitized 503. Delete is a hard delete. The local React memory manager provides explicit list/filter/search/create/edit/delete controls and an in-memory-only token lifecycle. Legacy rows without owner IDs remain inaccessible.

Memory retrieval is controlled by `JARVIS_MEMORY_RETRIEVAL_ENABLED` (default false) and requires persistence to be enabled. At most the configured 1–5 records (default 3) are selected by lexical search. Only bounded record ID/category/content fields are passed through typed `RequestContext`; the orchestrator frames their serialized content as untrusted reference data and adds a system instruction that it cannot override policy or the current user request. Retrieval failures fall back to a request context with no memories. The additive `/chat` `memory_context` response is `null` when retrieval is disabled; otherwise it reports `success`, `empty`, or `fallback` and only IDs of records actually supplied to the provider. It does not expose memory content, category, or source reference. Metadata-only diagnostics report outcome, duration in milliseconds, returned record count, and execution ID; they exclude query text, memory identifiers/content, category/source, credentials, and exception details. The original chat message is still the only user content saved by conversation persistence. Memory creation is always explicit through the API; no automatic extraction or chat-history copying exists.

Memory lifecycle semantics allow duplicate content as independent records with distinct IDs. PATCH changes supplied fields only: `null` clears category/source reference, but content cannot be cleared; empty patches are invalid. Any successful PATCH refreshes `updated_at`, even when the supplied value equals the current value. DELETE is permanent; the first delete succeeds and subsequent deletes return not found. These operations use the existing schema and require no migration.

Expert definitions are persona metadata, not seven independent agent implementations: each configured expert calls the same selected provider contract. The version-2 expert registry stores ordered deterministic classification phrase rules and output-contract IDs. Contract IDs are constrained by a Pydantic literal and resolved by a fixed Python allowlist; configuration cannot import modules, resolve arbitrary classes, or run code. Analysis and Validation experts require their matching contracts; other personas cannot declare those contracts. Their existing configured system instructions and Pydantic output contracts remain unchanged. The analysis contract captures a summary, bounded factors, evidence-supported conclusions, assumptions, missing information, and recommendations. The validation contract captures findings with supported/contradicted/uncertain verdicts, rationale and evidence, plus assumptions, missing information, and recommendations. Supported or contradicted claims require evidence. The provider protocol accepts an optional response model; the OpenAI adapter sends it as Chat Completions strict `json_schema` output. It transforms a copied schema by removing string/array size-bound keywords and documented unsupported composition keywords, while preserving required fields, object closure, references, definitions, and type/enum structure. The [OpenAI Structured Outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs) documents `maxItems` for standard models but excludes array bounds for fine-tuned models; since the selected model is configurable and live compatibility is unverified, all array bounds are omitted from the request schema. Pydantic continues to enforce all original bounds and semantic validators on returned JSON before synthesis. Unknown schema keywords, invalid references, or non-closed/non-required objects fail with sanitized permanent errors before network I/O. Structured requests use a bounded 8,192 completion-token allowance (ordinary text remains at 1,024); a truncated structured completion is rejected. The mock ignores instructions and returns its existing deterministic text with `assessment_status=not_evaluated` and empty specialist collections. Synthesis renders validated fields as readable text; public `/chat` fields remain unchanged. Structured validation enforces shape and bounds, not semantic quality. Provider identity and the `demo` flag distinguish mock output from model output. The OpenAI adapter uses a configured key, model, endpoint and explicit connection/read timeouts; only 429, 5xx and transport timeouts are eligible for the orchestrator's bounded retries. Authentication, refusal, malformed output, truncation, and other permanent errors are not retried, and API errors/logs do not include provider response bodies or credential values. Mocked tests verify outgoing schema construction, not live endpoint compatibility. Tool definitions are configuration data only. There is no tool executor, permission gateway, persistence, or external action path in this milestone. Audit events are returned in the internal orchestration result and are not persisted or exposed in the public chat body.

## Adding capabilities and providers

Future semantic/vector retrieval, document ingestion, model-driven planners/classifiers, capability registry, tool runtime, permission gateway, and independent verification modules should expose small typed interfaces and be assembled in the application/orchestration layer. Capability code should depend on those interfaces rather than a vendor SDK. A new model adapter implements `IntelligenceProvider`; configuration and router registration then select it. Keep credentials in environment-backed secret settings, never in logs or source. Tools that can affect external systems should be mediated by a separate permission/approval boundary and explicit bounded execution policy. The current OpenAI-compatible adapter makes only a text-completion request and does not expose tool calling.

## Reliability and persistence

Current request processing has a configurable timeout and sanitized failure boundary. Optional conversation and memory persistence use separate repository protocols and PostgreSQL adapters, instantiated only when `JARVIS_PERSISTENCE_ENABLED=true` and the psycopg persistence extra is installed. Connections use a bounded configurable connect timeout. A successful chat result is saved after orchestration as one transaction containing either a new conversation plus its first exchange or two appended messages on an existing conversation. Failure returns a sanitized 503 and does not report a saved success; an unknown supplied conversation ID is a distinct 404. Migration 0002 defines conversation tables; migration 0003 defines memory records and lexical search. Memory changes use parameterized SQL, bounded pagination, and sanitized errors. No automatic migration happens at app startup; use the existing database migration runner to apply migrations. Disabled mode does not import/connect to PostgreSQL. The health endpoint is process-level; readiness currently means startup configuration/provider/repository construction succeeded and does not probe the database.

The opt-in live PostgreSQL integration tests are isolated under `integration_tests/` so the ordinary offline unit suite does not require a server or PostgreSQL driver. They require an explicit environment opt-in, a password-free local-loopback maintenance URL, `PGPASSFILE`, the optional `persistence` dependency, and PostgreSQL client tools. The fixture creates a uniquely generated disposable database and removes only that database after the tests. Missing prerequisites are reported as skips; a skip is not evidence of live database compatibility. See [database/README.md](../database/README.md#opt-in-postgresql-integration-tests) for the exact PowerShell setup and safety constraints.

## Core v1.2 single-owner authentication boundary

When persistence is enabled, validated settings require a secret `JARVIS_LOCAL_AUTH_TOKEN` of at least 32 visible ASCII characters and a stable, non-nil `JARVIS_OWNER_ID` UUID. `authenticated_owner` is the shared dependency for every persistence-backed memory operation, chat request, and conversation-history request. It returns the configured owner only after a Bearer token comparison with `secrets.compare_digest`; clients cannot select an owner. Missing/invalid credentials return sanitized 401 with `WWW-Authenticate: Bearer`. Stateless mock chat remains unauthenticated when persistence is disabled.

Migration 0004 adds nullable memory `owner_id` with no default/backfill and an owner/listing index. Legacy rows remain NULL and invisible. Every memory count, retrieval, lookup and mutation query is scoped by owner; foreign and unknown memory UUIDs have the same 404 behavior. Conversation records do not have an owner column: the single configured credential gates all conversation reads/continuations/writes, so conversation UUIDs themselves are not an authorization boundary. This is a local single-owner prototype, not a tenant system. SQL predicates are not PostgreSQL row-level security. Plain HTTP bearer tokens are unsafe on untrusted networks, and XSS could access the frontend's in-memory credential. The frontend stores the token in React state only, sends it only to the configured API origin over HTTPS or loopback HTTP, and clears it after 401 or explicit Lock Workspace. No token is persisted or put in a Vite variable.
