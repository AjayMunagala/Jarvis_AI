1. Executive summary — what JARVIS is
-------------------------------------
JARVIS is a real-world, Iron Man-inspired, all-rounder Personal AI Operating System. It is not one model, not merely a chatbot, not only a voice assistant, and not only a coding agent. It is a modular software system built around replaceable AI models, shared context and memory, a planner/orchestrator, registered capabilities and tools, a permission gateway, and independent verification.

The intended interaction pattern is:
User states a goal → JARVIS understands it → gathers relevant context → plans bounded steps → selects suitable available capabilities → requests approval when required → executes permitted actions → observes evidence → verifies the outcome → records useful context → reports honestly.

The long-term goal is for the user to express outcomes in natural language and for JARVIS to work out the steps, use suitable tools, execute approved work, verify what happened, and explain the result. It should support voice and text, desktop and mobile interaction, coding and debugging, document and research intelligence, memory, personal administration, finance and forecasting, proactive monitoring, creative tools, smart home integrations, defensive security, learning, and controlled self-improvement.

The fictional JARVIS is inspiration, not a promise of unlimited or perfect capability. Real capabilities depend on supported APIs, hardware, operating-system restrictions, data access, permissions, model quality, and verifiable evidence.


2. Mission, success criteria, and non-goals
-------------------------------------------
Mission:
Build one dependable, extensible personal AI system that understands context, plans tasks, uses approved tools, verifies outcomes, remembers useful information, and improves through measured, controlled changes.

Core success criteria:
1. All-rounder: new domains can be added without abandoning the shared core.
2. Action-oriented: JARVIS can use real tools, not only produce prose.
3. Evidence-based: it distinguishes attempted, completed, and verified actions.
4. Model-independent: model providers can be changed through adapters.
5. Context-aware: approved memories and project knowledge improve relevant work.
6. Fault-tolerant: unrelated capabilities continue when one integration fails.
7. Secure: every tool has explicit scope, permissions, risk, timeout, and audit behaviour.
8. Recoverable: changes have version history, tests, backups where appropriate, and rollback paths.
9. Measurable: tests and evaluations determine whether code, workflows, and models improve.
10. Practical: start on existing hardware and add cost or infrastructure only when justified.

Non-goals:
• Do not train a huge language model from scratch as the first step.
• Do not start with dozens of microservices.
• Do not promise perfect reasoning, perfect market predictions, or unrestricted control of every device/application.
• Do not allow an LLM to bypass permission checks by generating a different command or tool request.
• Do not call an action successful without evidence.
• Do not silently change the project into a narrower product.


3. Complete capability inventory
--------------------------------
3.1 General intelligence and conversation
• Natural-language understanding, explanations, research, comparisons, planning, decision support, and bounded multi-step task decomposition.
• Confidence-aware communication that separates facts, evidence, assumptions, and forecasts.
• Specialist-agent coordination and response synthesis.

3.2 Voice
• Microphone input, speech activity detection, speech-to-text, natural responses, text-to-speech, interrupt/stop behaviour, and eventually a wake word.
• Text remains a fallback if speech recognition or synthesis is unavailable.
• Wake-word and continuous-background behaviour must respect OS and privacy constraints.

3.3 Desktop and computer interaction
• Supported application launching, project/file inspection, terminal use, browser interaction, logs, keyboard/mouse actions where justified, and repeatable workflows.
• Prefer explicit application APIs, IDE integrations, and browser automation over brittle blind clicking when possible.
• Computer actions must be scoped and permission-controlled.

3.4 Software engineering and debugging
• Repository scanning, code search, symbol/dependency understanding, Git inspection, log/API/database investigation, reproduction of bugs, patch creation, tests, builds, browser-based checks, regression testing, and evidence-based reporting.
• Preserve unrelated user changes. Inspect Git status and diff before modifying files.
• Ask for approval for sensitive operations such as commits, pushes, destructive changes, and production deployment according to configured policy.
• A code edit alone is not proof of a fix.

3.5 Documents, research, and knowledge
• Support suitable PDFs, DOCX, spreadsheets, text, source code, research papers, manuals, project files, and approved web sources.
• Extract content while preserving source metadata and references.
• Retrieve evidence for answers and identify conflicting sources.
• RAG and indexing are the initial knowledge strategy; fine-tuning is a separate later decision.

3.6 Memory
• Working memory: current request/task and temporary context.
• Episodic memory: selected past events, interactions, and outcomes.
• Semantic memory: curated facts and concepts.
• Project memory: architecture, technologies, decisions, bugs, tasks, important files, and status.
• User-approved preferences and long-term memories.
• Provide ways to correct, update, inspect, and delete stored memories. Avoid indiscriminate retention of every message.

3.7 Personal assistant and life administration
• Tasks, reminders, calendar, meeting support, daily briefings, conflict detection, email drafting/reading where connected, document organization, subscriptions/warranties, receipts, forms, and important dates.
• Bookings and external actions require a supported integration, authorization, any necessary confirmation, and verification of the resulting status.
• JARVIS must not claim a booking, email, or calendar change succeeded merely because it attempted it.

3.8 Phone and cross-device continuity
• Mobile voice/text interface, permitted notifications, supported controls, reminders, shared tasks and memory, and continuity between phone and desktop.
• React Native + TypeScript is the proposed mobile UI.
• Android and iOS have different restrictions; native integrations may be needed. Unrestricted control of all applications is not guaranteed.

3.9 Finance and markets
• Expense and budget analysis, savings goals, investment research, company/market news, financial indicators, scenario analysis, stock forecasting, and risk analysis.
• Combine data pipelines, quantitative/statistical/ML methods, fundamentals/news where available, and risk evaluation.
• Report uncertainty, assumptions, bullish/base/bearish scenarios, forecast ranges, and evaluation results.
• Backtest with out-of-sample data and account for costs, taxes, slippage, and leakage where relevant.
• No guaranteed returns; no autonomous real-money trading in the initial system.

3.10 Proactive monitoring and automation
• Configured monitoring of calendar events, tasks, Git/build pipelines, system health, security alerts, spending, market sources, and other permitted events.
• Event → rules → optional AI evaluation → importance filter → notification or approved workflow.
• Avoid noisy notifications; alert only when configured significance conditions are met.

3.11 Defensive cybersecurity and system health
• Help identify suspicious links, phishing indicators, exposed secrets in owned repositories, outdated dependencies, health problems, and backup failures.
• Provide explanations and remediation recommendations.
• Do not collect passwords or bypass security boundaries.

3.12 Smart home and physical devices
• Compatible lights, plugs, climate controls, sensors, and other supported devices through appropriate integrations such as Home Assistant.
• Physical actions require compatible hardware, authorization, and risk-aware policies.

3.13 Tutor and skill development
• Explain concepts at the user's level, create exercises, build study plans, track progress, and test understanding.

3.14 Creative tools
• Assist with reports, presentations, diagrams, images, audio/video workflows, writing, and organizing creative assets.

3.15 Travel and decision intelligence
• Compare routes/options, plan itineraries, organize bookings, track departure times, model alternatives, estimate costs, and explain trade-offs.

3.16 Controlled self-improvement
• Learn from approved outcomes, improve tools/workflows, propose source-code changes, generate tests, evaluate candidate models, promote validated updates with approval where required, and support rollback.


4. System architecture and module boundaries
--------------------------------------------
The system begins as a modular monolith: one application with clear module interfaces. Do not create dozens of independently deployed services before there is a concrete operational reason. Extract a module into a service only when scale, isolation, deployment, or reliability requirements justify it.

Logical layers:
1. Interfaces: web/desktop, mobile, text, voice, notifications.
2. API boundary: request validation, authentication where needed, limits, correlation IDs, and response schemas.
3. JARVIS core: request context, intent understanding, model routing, orchestration, and response synthesis.
4. Planner: produces a bounded plan with explicit steps, required capabilities, expected outcomes, and risk classification.
5. Capability manager/registry: describes what is available, health status, input/output schema, permissions, timeout, and failure behaviour.
6. Specialist agents: coding, research, knowledge, finance, personal planning, browser, system, and future domains.
7. Tool registry/runtime: validates tool inputs, checks permission, runs approved operations, enforces timeouts/limits, captures results, and emits audit events.
8. Memory and knowledge: persistent data, project memory, document retrieval, and optional semantic/vector retrieval.
9. Event engine/scheduler: scheduled jobs, monitored events, triggers, and notification policies.
10. Verification engine: checks observable outcomes independently of the model's claims.
11. Security and approval gateway: enforces authorization and confirmation rules.
12. Observability/recovery: logs, traces, health/readiness, bounded retries, circuit breakers where useful, backups, versioning, and rollback.
13. Self-improvement pipeline: candidate changes/models, sandboxing, evaluations, approval, rollout, monitoring, rollback.

5. Mother, Planner, experts, registry, and runtime
--------------------------------------------------
The original architecture idea uses a Mother/orchestrator and a Planner, with specialist experts/capabilities selected from a registry.

Mother/orchestrator:
• Understands the request and available context.
• Determines whether the request needs a simple answer, a tool, one specialist, or a multi-step plan.
• Coordinates bounded execution.
• Synthesizes results and reports uncertainty/failures.

Planner:
• Creates a structured, bounded plan.
• Identifies dependencies, required capabilities, expected outputs, risk, and verification conditions.
• Uses sequential execution by default; parallel execution only when dependencies and safety permit.
• Does not grant permissions. A plan cannot override the permission gateway.
• Execution/tool rounds are bounded; the earlier architecture discussion proposed a maximum of five tool rounds as an initial guard, configurable and testable.

Expert/capability registry:
• Describes available experts/capabilities and their contracts.
• Initial conceptual expert categories included Recommendation, Analysis, Validation, Risk, Compliance, Architecture, and Knowledge.
• Later capability areas include Coding, Browser, Personal Assistant, Finance, Voice, System, and Creative.
• Register capabilities as interfaces and metadata; do not hardcode all routing logic into one giant function.

Tool registry:
• Describes tool name, purpose, input/output schema, permissions, risk, timeout, resource limits, and audit requirements.
• Initial examples: calculator, read-only file search, Git status/diff, knowledge search, vendor/data lookup, approved API/database reads, terminal/test runner, browser automation.
• Read-only tools should be implemented before tools that mutate data or the operating system.
• External APIs and database operations must be explicitly scoped.

Execution contract:
Request → validated plan → capability selection → policy check → tool execution → typed result → independent verification → response.
Tool results must distinguish success, failure, timeout, unavailable capability, denied permission, and partial result.


6. Shared protocols and structured contracts
--------------------------------------------
Use typed, versioned contracts between modules so new capabilities can be added without rewriting the core.

Minimum conceptual contracts:
• RequestContext: request ID, user/session identity, timestamp, locale/time zone where relevant, active project, relevant memory references, policy context, cancellation/deadline.
• Plan: plan ID, steps, dependencies, required capability IDs, expected outcomes, risk class, verification criteria, status.
• CapabilityDescriptor: ID/version, description, availability/health, input schema, output schema, required permissions, timeout, resource limits, supported modes.
• ToolCall: call ID, tool ID/version, validated arguments, authorization context, deadline, correlation ID.
• ToolResult: status, typed output, sanitized error, evidence references, duration, side effects, retryability.
• ApprovalRequest: action, target, reason, risk, expected side effects, exact scope, expiry, approval state.
• AuditEvent: event ID, request/plan/tool IDs, timestamp, action, actor, authorization decision, result, evidence references, and redaction metadata.
• VerificationResult: criteria, checks executed, observed evidence, pass/fail/blocked/partial status, limitations.
• MemoryRecord: type, content, source/provenance, sensitivity, created/updated times, confidence, expiry/review policy, user correction/deletion state.
• Event: source, type, timestamp, payload schema, deduplication key, trigger rule, importance, action policy.
• ModelAdapter contract: provider/model identity, capabilities, structured input/output, timeout, usage/cost metadata where available, and normalized errors.

All external/model-generated structured outputs must be schema-validated. Treat model output as untrusted input. Version contracts and maintain conformance tests.


7. Model strategy and hardware
------------------------------
JARVIS is a system built around models; it is not a model trained from scratch.

Model strategy:
• Define a provider-neutral interface.
• Keep the mock provider for offline tests.
• Add a hosted provider and/or local model behind the same interface.
• Later use a model router for suitable fast, reasoning, vision, speech, embedding, or specialist models.
• Select models using measured quality, latency, privacy, context length, cost, licensing, hardware, and tool-use performance.
• Maintain fallback models only where they are configured and compatible.
• Do not assume a model fallback is always available.

Hardware strategy:
• Start with the existing Windows development computer; a dedicated GPU is not a prerequisite for API/backend development, mock tests, PostgreSQL, small tools, or many statistical workloads.
• Hosted model APIs can be used if the user chooses and accepts connectivity, privacy, and cost implications.
• Small CPU-based local models may work but can be slower or more limited.
• GPU/local serving such as vLLM is a later decision based on actual memory/VRAM and performance measurements.
• Fine-tuning and large-scale training are not prerequisites for the initial milestones.
• Do not buy a GPU before a measured need is established.

Privacy:
• Keep secrets out of source control.
• Use environment/configuration for provider settings and secret stores where appropriate.
• Decide explicitly which data may be sent to external models/services.


8. Memory, documents, and knowledge pipeline
--------------------------------------------
Initial persistence recommendation: PostgreSQL as the primary database. Add pgvector when semantic retrieval is needed. Avoid introducing multiple databases without a demonstrated requirement.

Document pipeline:
1. Discover/import supported files from explicitly authorized locations.
2. Validate type, size, access rights, and parsing safety.
3. Extract text/tables/metadata.
4. Preserve source identity, file/page/section where possible, timestamps, and checksums.
5. Chunk content with source references.
6. Index for lexical and, when appropriate, semantic retrieval.
7. Retrieve relevant passages for a question/task.
8. Provide evidence references in the response.
9. Track stale/changed documents and re-index as needed.
10. Respect deletion and access-control changes.

Memory lifecycle:
• Capture only information with a useful purpose.
• Classify as working, episodic, semantic, project, or preference memory.
• Store provenance and confidence.
• Retrieve only relevant memory for a task.
• Update stale facts; avoid treating outdated plans as current truth.
• Allow user inspection, correction, and deletion.
• Separate raw conversation history from curated long-term memory.

RAG versus fine-tuning:
• RAG retrieves relevant source information at answer time.
• Memory stores selected user/project context.
• Fine-tuning changes model behaviour for targeted tasks.
• Continued training updates model weights and requires carefully prepared data/evaluation.
These mechanisms are different and must not be conflated.


9. Coding agent and independent verification
--------------------------------------------
The coding/debugging agent is an early flagship capability, but it is one module within the all-rounder JARVIS.

Conceptual coding workflow:
1. Identify repository and active branch.
2. Inspect Git status and diff before changing anything.
3. Map relevant files, symbols, dependencies, routes, and data flow.
4. Understand the user's expected behaviour and reproduce the failure when possible.
5. Capture baseline tests/build/runtime evidence.
6. Investigate frontend, API, backend, database, logs, and browser as permitted.
7. Explain the likely root cause and proposed scope.
8. Make the smallest justified patch within authorized workspace boundaries.
9. Run targeted tests, then broader tests/build/lint as appropriate.
10. Use Playwright or other integration checks when relevant and safe.
11. Reproduce the original scenario and test for regressions.
12. Review the final diff; ensure unrelated user changes are preserved.
13. Report changed files, commands, actual results, untested areas, and confidence.
14. Ask for confirmation before actions that policy classifies as requiring approval.

Verification rules:
• A generated answer is not evidence that an operation succeeded.
• A test is only reported as passing if it actually ran and passed.
• If a test cannot run, state why and mark verification as incomplete.
• Use a bounded repair/test loop with a maximum iteration limit.
• Keep test output and relevant evidence references.
• Do not automatically commit, push, deploy, or run destructive operations without the required authorization.

Repository intelligence (RIE/LIE concept):
• Scan project structure, language/frameworks, dependencies, symbols, relationships, and relevant configuration.
• Return focused context to the model rather than dumping an entire repository into every prompt.
• Integrate incrementally; do not claim an existing RIE/LIE implementation unless the repository proves it.


10. Security, privacy, permissions, and approvals
-------------------------------------------------
Security must be a foundation for real tool execution, not a later patch.

Principles:
• Least privilege: each tool receives only the access required for its task.
• Deny by default for unregistered/unapproved operations.
• Validate all arguments and normalize paths/targets.
• Keep secrets out of prompts, logs, Git, and error messages.
• Use timeouts, output-size limits, rate limits, and resource limits.
• Treat files, websites, emails, tool results, and model outputs as untrusted data.
• Keep audit records but redact secrets and sensitive content.
• Separate read-only access from mutation/execution access.
• Use sandboxing for risky code execution and self-modification.
• Apply authentication and authorization before exposing services beyond the trusted local boundary.
• Use backups, versioning, rollback, and recovery tests.
• Never allow the model to bypass policy checks by rephrasing a tool call.

Illustrative risk policy:
LOW: answer, calculate, search authorized data, read permitted files → usually automatic.
MEDIUM: run approved tests, make bounded workspace changes, update noncritical task records → policy-controlled; may require confirmation.
HIGH: delete data, change important configuration, send external communications, commit/push code, modify credentials → explicit confirmation according to configured policy.
CRITICAL: production deployment, financial transactions, destructive database operations, or similarly consequential changes → explicit authorization, scope confirmation, strong checks, and audit.

The exact classification must be configurable and reviewed against actual tools. A tool's description must not be the only enforcement mechanism; enforcement belongs in code outside the LLM.


11. Fault isolation and graceful degradation
--------------------------------------------
Fundamental rule: failure of one capability must not unnecessarily cause failure of unrelated capabilities.

Required design techniques as the system grows:
• Module boundaries and typed interfaces.
• Timeouts and cancellation.
• Bounded retries with exponential backoff only for retryable failures.
• Circuit breakers for repeatedly failing dependencies where useful.
• Health/readiness status per capability.
• Partial results when useful and safe.
• Provider/tool fallback only when explicitly configured and semantically suitable.
• Local cache only where stale data is acceptable and clearly labelled.
• Clear distinction between unavailable, denied, failed, timed out, partial, and verified.
• No silent substitution that changes the meaning of a task.
• Integration and chaos/failure tests for critical boundaries.

Examples:
• TTS fails → return text.
• Browser automation fails → report browser unavailable and continue independent analysis.
• One model provider fails → use a configured compatible fallback or report the limitation.
• Database is unavailable → only use a safe cache/limited mode if explicitly designed; do not pretend writes persisted.
• Finance data feed fails → do not produce a fresh-data forecast as though data were current.


12. Proactive event engine and scheduling
-----------------------------------------
The event engine allows JARVIS to notify the user or start permitted workflows without requiring a new manual prompt.

Pipeline:
Event source → validation/deduplication → rule evaluation → optional AI analysis → importance/urgency assessment → permission policy → notification or approved workflow → verification → audit.

Potential sources:
• Calendar and reminders.
• Git repositories, CI/build pipelines, and project status.
• System health and backups.
• Security alerts.
• Budget/expense data.
• Market/news feeds.
• Supported device and smart-home events.

Requirements:
• Explicit opt-in for each monitored source and scope.
• Configurable schedules, quiet hours, thresholds, and notification preferences.
• Deduplication and rate limiting.
• Expiring or revocable credentials.
• Avoid noisy repeated alerts.
• Do not autonomously perform high-risk actions merely because an event triggered.
• Keep the event engine independent from optional integrations so a failed feed does not stop the whole core.


13. Mobile, desktop, voice, and smart-home integration
------------------------------------------------------
Shared-core approach:
• One JARVIS backend owns orchestration, permissions, shared tasks, memory, and audit.
• Desktop/web UI and mobile UI are clients of that backend.
• Voice is an input/output channel, not a separate intelligence system.
• Device-specific functionality lives behind capability adapters.

Desktop:
• Begin with a web UI or simple local client.
• Use application APIs, IDE extensions, browser automation, and scoped system tools where possible.
• Add deeper OS integration only after permissions and audit controls are in place.

Mobile:
• React Native + TypeScript is the proposed shared UI technology.
• Use native Android/iOS APIs where required and permitted.
• Keep platform-specific limitations visible to the planner and user.
• Cross-device sync must be authenticated and encrypted appropriately.

Voice:
Microphone → voice activity detection → STT → request context/orchestrator → response → TTS → speaker.
Include interruption, timeouts, and text fallback.

Smart home:
• Integrate through supported platforms/protocols, potentially Home Assistant.
• Device action risk depends on physical consequences.
• Require confirmation or stricter policies for consequential physical operations.


14. Finance, forecasts, and quantitative evaluation
---------------------------------------------------
Finance must be a specialist capability with data provenance and quantitative checks; a general LLM alone is not a reliable stock-price forecasting engine.

Possible pipeline:
Data sources → quality/freshness checks → feature construction → baseline/statistical/ML models → scenario forecasts → uncertainty/risk analysis → out-of-sample evaluation → user-facing explanation.

Data may include prices, volume, filings, earnings, economic indicators, news, and other appropriately licensed sources.

Requirements:
• Display data timestamps and provider limitations.
• Distinguish observed facts, derived metrics, assumptions, and predictions.
• Compare models against simple baselines.
• Use walk-forward or other appropriate out-of-sample evaluation.
• Avoid look-ahead and survivorship bias.
• Include costs, taxes, and slippage when evaluating trading strategies where relevant.
• Report uncertainty and failure cases.
• Do not promise profits or certainty.
• Start with analysis and planning; no autonomous real-money trading in the initial system.
• Keep private financial data protected and restrict external sharing.


15. Controlled self-improvement and model lifecycle
---------------------------------------------------
JARVIS must not freely rewrite and deploy itself. Self-improvement is a controlled development/evaluation workflow.

Three levels:
1. Memory-based adaptation: retain approved preferences, corrections, outcomes, and successful workflows.
2. Tool/workflow improvement: propose code or workflow changes, create tests, evaluate in an isolated environment, review diff, approve, and roll back if necessary.
3. Model training/update: prepare approved training data, version datasets, train candidate models, evaluate against a fixed suite, compare with the incumbent, and promote only when criteria are met.

Candidate lifecycle:
Observe weakness → formulate measurable hypothesis → create candidate → isolate/sandbox → test security and correctness → run regression/evaluation suite → compare with current version → review change and evidence → approve → deploy gradually → monitor → rollback if needed.

Requirements:
• Never modify the only working copy without recoverability.
• Keep versioned source, datasets, configurations, model artifacts, and evaluation results.
• Establish objective acceptance criteria before training or changes.
• Protect credentials and user data.
• Keep a manual override/stop mechanism.
• No self-granted permission escalation.
• Failed candidate changes must not disable the currently working version.


16. Observability, testing, and operational quality
---------------------------------------------------
Every milestone should include tests and evidence, not only implementation.

Test layers:
• Unit tests for validation, policies, schemas, tools, and state transitions.
• Contract tests for providers, capabilities, and tool adapters.
• API/integration tests for request-to-result workflows.
• Failure tests for timeout, exceptions, malformed model output, missing dependencies, and partial results.
• Security tests for unauthorized tools, path escapes, secret leakage, and policy bypass attempts.
• End-to-end tests for key user workflows.
• Regression tests for previously fixed defects.
• Evaluation suites for model quality and self-improvement.
• Recovery tests for rollback and restart where applicable.

Operational practices:
• Structured logs with correlation/request IDs.
• Redaction of secrets and sensitive data.
• Health endpoint versus readiness endpoint semantics.
• Metrics for latency, failures, tool calls, retries, cost where measurable, and verification status.
• Clear user-visible status: planned, running, succeeded, failed, partially completed, blocked, or verified.
• Do not claim tests passed unless their execution output supports that claim.

18. Implementation roadmap and acceptance gates
-----------------------------------------------
Phase 0 — Vision and architecture
Deliverables: master reference, module boundaries, contracts, security principles, roadmap, versioning and change-control process.
Gate: a new developer can explain the goal, architecture, safety model, and next milestone from these documents.

Phase 1 — Core v0.1 verification
Deliverables: run existing tests, fix failures, verify startup/API/limits/timeouts, clean documentation, record actual test results.
Gate: current mock-backed API is reproducibly tested; known limitations are explicit.

Phase 2 — Core v0.2 orchestration foundation
Deliverables: orchestration service and request context; provider contract/conformance tests; typed capability/tool interfaces; audit-event schemas; bounded execution policy; graceful error/partial-result handling.
Gate: request → context → orchestration → validated response works through interfaces, and provider failures/timeouts are tested. Do not yet add unrestricted real-world actions.

Phase 3 — Real model adapter
Deliverables: at least one real model provider behind the adapter; secrets via environment/configuration; timeout, error normalization, structured-output validation, usage/cost tracking where available.
Gate: provider can be swapped without changing the API/orchestrator contract; mock remains usable for tests.

Phase 4 — Safe read-only tools
Deliverables: calculator, authorized file/project search, Git status/diff, knowledge search; tool schemas, timeouts, permissions, audit events.
Gate: planner can choose and execute a registered read-only tool, return evidence, and report unavailable/denied/error states correctly.

Phase 5 — Persistent memory and knowledge
Deliverables: PostgreSQL schema/migrations, conversation/task/project records, approved memory lifecycle, backups, retrieval interfaces; pgvector/document ingestion when justified.
Gate: data persists across restart; retrieval is scoped and evidence/provenance is preserved; deletion/correction works.

Phase 6 — First complete action loop
Deliverables: bounded planner, capability availability checks, tool runtime, independent verification, clear result reporting.
Gate: a real read-only task goes from request through planning, tool execution, evidence verification, and honest report.

Phase 7 — Coding and repository intelligence
Deliverables: repo scanner, Git safety, code search, diagnostics, patch manager, controlled test/build runner, bounded repair loop.
Gate: a chosen bug/task can be investigated and tested without overwriting unrelated changes; unverified fixes are clearly labelled.

Phase 8 — Browser verification
Deliverables: Playwright integration, DOM/console/network checks, screenshots where useful, reproducible E2E scenarios.
Gate: at least one real application workflow is verified with recorded evidence.

Phase 9 — Voice and interface
Deliverables: web UI, STT/TTS, interruption, text fallback, permission-aware microphone handling.
Gate: a voice request reaches the same core and produces a usable response; text remains available on voice failure.

Phase 10 — Personal assistant and mobile
Deliverables: tasks, reminders, calendar integrations, approved email/booking workflows, mobile client, authenticated cross-device sync.
Gate: connected actions are verified with service results and policy/approval is enforced.

Phase 11 — Proactive event engine
Deliverables: opt-in sources, scheduler, deduplication, rules, importance filter, notifications, audit.
Gate: a configured event creates a correctly scoped, non-spammy alert; failed feeds are isolated.

Phase 12 — Finance and quantitative intelligence
Deliverables: data ingestion, data-quality checks, baselines, forecast models, risk/scenario reports, backtesting and monitoring.
Gate: forecasts are timestamped, evaluated out of sample, uncertainty-aware, and never presented as guaranteed.

Phase 13 — Security/system, smart home, tutor, creative, travel and life administration
Deliverables: integrations delivered as separate capability modules with contracts, permissions, health and tests.
Gate: each capability has explicit scope, tested failure handling, and documented OS/provider limitations.

Phase 14 — Controlled self-improvement
Deliverables: candidate branch/artifact workflow, sandbox, evaluation suite, approval, rollout, audit, rollback.
Gate: a candidate can be rejected safely, or promoted only after measurable acceptance criteria are met.

Phase 15 — Advanced JARVIS
Deliverables: multi-model routing, knowledge graph, broader device integrations, stronger proactive workflows, additional services only when justified.
Gate: additions preserve backwards compatibility, security, reliability, and the complete vision.


19. Milestone tracking and change control
-----------------------------------------
Maintain a separate status ledger with one row per feature or milestone and fields:
ID, feature, phase, status, evidence, tests run, known gaps, dependencies, next action, last verified commit/date.

Allowed status values:
• NOT STARTED
• IN PROGRESS
• IMPLEMENTED
• TESTED
• VERIFIED
• BLOCKED
• DEFERRED (with reason)

For each milestone:
1. Read the relevant architecture and handoff docs.
2. Inspect Git status and the current branch.
3. Confirm the milestone's scope and acceptance criteria.
4. Implement only the agreed scope.
5. Run targeted and relevant regression tests.
6. Review diffs and security implications.
7. Record actual command outputs and known gaps.
8. Update README/ROADMAP/HANDOFF/status ledger.
9. Commit only according to the user's workflow and permissions.
10. Reconcile the master reference only when an architectural decision is intentionally changed.

Change-control rule:
New ideas are welcome, but they do not silently replace the master goal. Classify each proposal as:
A. Add capability without changing the core.
B. Refine an existing design.
C. Change a prior decision.
For C, document reason, alternatives, consequences, migration, and approval before treating it as the new direction.

21. Glossary for future readers
-------------------------------
Agent: A component that handles a defined kind of task using a model and/or tools.
API: A defined interface that lets software components communicate.
Audit event: A record of what action was requested, authorized, executed, and observed.
Capability: A declared ability JARVIS can use, such as project search or calendar lookup.
Circuit breaker: A mechanism that temporarily stops calling a repeatedly failing dependency.
Contract test: A test that checks whether a provider/tool follows its agreed input/output interface.
Fault isolation: Containing a failure so unrelated components can continue.
Graceful degradation: Continuing with reduced functionality when optional components are unavailable.
LLM: Large language model; a model used for language understanding/generation and related reasoning tasks.
Mother/orchestrator: The central coordinator that understands a task and coordinates specialists.
Planner: A component that creates a structured, bounded execution plan.
RAG: Retrieval-augmented generation; retrieve relevant source material and provide it to a model for answering.
RIE/LIE: Repository/project intelligence concepts discussed for indexing project structure, symbols, dependencies and relationships.
Sandbox: An isolated environment used to test potentially risky code or changes.
STT: Speech-to-text.
TTS: Text-to-speech.
Tool: A callable function or integration that performs a defined operation.
Verification: Checking observable evidence to determine whether the intended outcome actually occurred.
Vector search: Similarity-based retrieval using numerical representations of content.


22. Master rule — preserve the vision
-------------------------------------
JARVIS remains an all-rounder Personal AI Operating System.

It must not be redefined as only:
• a chatbot,
• a voice assistant,
• a coding agent,
• a stock predictor,
• a collection of unrelated scripts, or
• a single vendor's model wrapper.

The core is designed once, with modular capabilities added in stages. Each capability must use defined interfaces, respect permissions, handle failure, and provide evidence of outcomes. Models and external services are replaceable. Memory is user-controlled. Self-improvement is evaluated and recoverable. The roadmap may evolve, but only through explicit, documented decisions.

When unsure what to do next, read this master reference, then inspect the repository's docs/ROADMAP.md, docs/HANDOFF.md, current Git state, and tests. Determine the last verified milestone, then continue with its next acceptance criteria. Never guess that work is complete.
